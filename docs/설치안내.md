# 직접 배포하는 순서

## 1. Supabase

1. 사용할 Supabase 프로젝트를 만듭니다. 이 앱은 사용자 로그인 기능을 사용하지 않습니다.
2. SQL Editor를 열고 **`sql/001_gold_board.sql` 전체**를 붙여 넣어 실행합니다.
3. Table Editor에서 `gold_daily`, `gold_state`가 생겼는지 확인합니다. `gold_state`에는 id=1 한 행이 있고, `gold_daily`는 처음에는 비어 있습니다.
4. 프로젝트 연결/API 설정에서 프로젝트 URL과 서버 전용 **legacy `service_role` 키**를 확인합니다. 이 구현에서 사용하는 키 이름은 `SUPABASE_SERVICE_ROLE_KEY`입니다. `anon`/publishable 키로 대체하지 않습니다.

SQL은 `gold_*` 객체만 만듭니다. 기존 카드 편집기 등 다른 테이블은 건드리지 않습니다. 같은 스키마를 재실행해도 데이터를 삭제하지 않습니다.

## 2. GitHub

1. 이번 과제용 새 **Public** 저장소를 만듭니다. 예: `gold-information-board`.
2. 압축을 풀고 `gold-board` 폴더 **안의 파일과 폴더 전체**를 올립니다. 저장소 첫 화면에서 `package.json`, `vercel.json`, `api/`, `public/`이 보여야 합니다.
3. 실제 키가 들어 있는 `.env.local`은 올리지 않습니다. 제공한 `.env.example`에는 자리표시자만 있습니다.

`public` 폴더나 `dist` 폴더만 올리면 서버 기능과 DB 저장이 작동하지 않습니다.

## 3. Vercel

1. 새 프로젝트에서 GitHub 저장소를 가져옵니다.
2. Framework Preset은 **Other**, Build Command는 **`npm run build`**, Output Directory는 **`dist`**로 설정합니다. Node.js는 **24.x**를 사용합니다. Root Directory는 `package.json`이 있는 폴더입니다.
3. Environment Variables에 아래 3개를 넣습니다. 적어도 Production 환경에 적용해야 합니다.

| 이름 | 넣을 값 |
|---|---|
| `SUPABASE_URL` | `https://프로젝트식별자.supabase.co` 형태의 프로젝트 URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase 서버 전용 `service_role` 키 원문 |
| `CRON_SECRET` | 무작위 비밀문자열 (권장 32자 이상) |

CRON_SECRET은 Node.js가 설치된 본인 PC에서 다음 명령으로 만들 수 있습니다. 생성 결과는 Vercel 환경변수에만 입력합니다.

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

4. Deploy를 누릅니다. 나중에 환경변수를 수정했다면 **Redeploy**해야 적용됩니다.
5. Production 주소를 새 시크릿 창에서 엽니다. Vercel 로그인 화면이 보이면 이 과제의 공개 접근 조건을 만족하지 못합니다. 과제용 프로젝트의 Deployment Protection 설정을 확인하고 **제출할 Production 주소**가 로그인 없이 열리도록 설정합니다.

## 4. 첫날 실제 기록

1. 실제 금시세 조회를 누릅니다.
2. 가격·단위·출처·원천 시각·조회 시각과 한국 날짜 행 1개가 보이는지 확인합니다.
3. 30초 이상의 대기 후 다시 조회해 같은 날짜가 1행인지 확인합니다. 가격이 바뀌면 그 행의 마지막 성공값이 갱신됩니다.
4. 원자료 대조 보기에서 원자료 price, 저장값, 화면값을 비교합니다.

원천이 늦으면 12초에 시간초과로 처리합니다. 처음부터 원천이 실패하면 없는 가격을 만들지 않으므로 표시값은 `—`입니다. 나중에 성공하면 정상으로 전환됩니다.

## 5. 다섯 실패 시험

1. 실패 재생실을 누릅니다.
2. 다섯 실패 자동 검사를 누릅니다.
3. 자체 검사 5종 결과를 확인합니다. 수동으로도 D1-A → D1-B → 실패 → D2 정상 복구를 누를 수 있습니다.

느림, 401/403 거절, 429, 오프라인, 형식 변경에서 각각 다른 오류가 보여야 합니다. 실패 때 가격 3,010 합성값과 1행이 유지되고, D2 복구 후 3,040 합성값·2행·fresh/none이 보여야 합니다. 이 숫자는 **합성 시험 전용**입니다.

별도의 ‘공식 T04 검사’ 링크에서 원본 hash와 fixture를 검사하세요. 자체 시험은 추가 회귀 검사로 유지했습니다.

## 6. 둘째 날 실제 기록

첫 조회와 다른 **실제 KST 날짜**에 실제 금시세 조회를 누릅니다. 가능하면 바로 다음 날에 수행합니다.

- 한국 자정 이후가 다음 날짜입니다. PC 날짜를 바꾸거나 데이터를 직접 삽입하지 않습니다.
- `vercel.json`의 예약 실행은 매일 UTC 00:10, 즉 KST 09:10입니다. Production 배포에서만 작동하며 공급자 정책에 따라 실행이 지연될 수 있습니다.
- 예약 작업이 실패하면 그날 직접 실제 조회를 누릅니다. 실패가 성공 기록을 만들어 주지는 않습니다.
- 기록 대조에 실제 2/2건이 보이면 변화액·변화율을 다시 계산하고 **증빙 JSON 다운로드**를 누릅니다.
- 첫날과 둘째 날의 가격이 같으면 변화액 0도 정상입니다. 휴장 때 원천 시각은 오래된 것으로 표시됩니다.

## 7. 제출 URL

- 결과물: 공개 Production URL.
- 소스: 저장소 첫 화면이 아닌 **고정 커밋 URL**. GitHub의 해당 커밋 화면에서 주소를 복사합니다. `https://github.com/소유자/저장소/commit/실제전체해시` 형태여야 하며 전체 소문자 해시는 40자리 또는 64자리입니다.
- 두 주소 모두 새 시크릿 창에서 로그인·초대·비밀번호·CAPTCHA 없이 확인합니다.
- `docs/제출문.md`의 빈칸을 실제 주소로 채웁니다.

## 문제별 확인

| 화면 | 확인할 내용 |
|---|---|
| 서비스 연결 대기 | Vercel 환경변수 3개, Production 적용, 재배포 |
| 저장소 연결 실패 | SQL 실행 여부, URL, service_role 키, Supabase 프로젝트 상태 |
| 응답 지연 | 출처 응답이 12초를 초과. 잠시 뒤 재시도 |
| 원천 접근 거절 | 원천 서비스 상태 확인. 사용자에게 로그인하라고 요구하는 오류가 아님 |
| 호출 제한 | 표시된 재시도 시간이 지난 후 재조회 |
| 네트워크 연결 실패 | 인터넷 및 원천 연결 확인 |
| 형식 변경 | 원천 스키마를 확인하고 `public/core.mjs`의 검증 규칙 검토 |
| 오래된 값 | 원천 관측/조회 시각 확인. 휴장·갱신 지연일 수 있음 |
| 기록 1/2건 | 다른 실제 한국 날짜에 조회 성공 필요 |

개인정보, 사용자 IP, 이메일, 로그인 기록을 앱 DB에 저장하지 않습니다. 배포 사업자의 운영 로그는 별도 서비스 정책을 따릅니다. 과제 제출 시 본인 계정 화면이나 키가 보이는 화면을 첨부하지 마세요.
