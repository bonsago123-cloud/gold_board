# 실제 사이트 전체 기능 실행 규칙

이 문서는 저장소를 이어받는 모든 AI에게 적용한다. 역할 이름이나 이전 대화는 필요 없다.
사용자가 문서 수정 등 범위를 한정한 작업은 그 범위대로 수행하고 기능 검증 여부를 별도로 밝힌다. 일반적인 “이어서 진행해”에는 아래 전체 절차를 적용한다.

## 1. 시작: 조건과 기능 목록 확인
- 저장소의 과제 조건, AGENTS.md, 현재 인수인계, 이전 기능 검사 결과를 읽는다. 과제 조건 원문을 찾지 못하면 누락으로 기록한다. 과거 고정 10개 검사·기대값·공통 사용 상한·사용량 기록을 바꾸지 않는다.
- 실제 배포 주소는 https://goldboard-omega.vercel.app 이다. 로그인 없는 새 브라우저 세션에서 시작한다. 검사 시각·시간대·소스 커밋·배포 버전 확인 여부·사용한 브라우저를 기록한다. 배포 버전을 확인 못 하면 추정하지 않는다.
- 화면, 페이지 링크, 소스의 페이지·이벤트를 함께 살펴 기능 목록을 만든다. 아래 시작 목록에 없는 기능, 동적으로 생긴 버튼, 숨겨진 오류 상태의 재시도도 추가한다. 소스를 읽은 것만으로 실행했다고 적지 않는다.

## 2. 모든 기능을 직접 실행
각 버튼·탭·입력·선택값·다운로드·링크를 적어도 한 번 사용한다. 클릭했다는 사실보다 기대한 결과가 실제로 나타나는지 확인한다. 로딩이 끝날 때까지 합리적인 제한 시간 안에서 기다린다. 계속 로딩이면 실패 또는 미검사 사유를 남긴다.

| 페이지 | 기능 목록 작성의 시작점 |
|---|---|
| / | 금·은 각각의 탭/실제 조회, USD·KRW 가격/단위/원천 및 조회 시각, 자동 조회 켜기·실제 갱신 확인·끄기, 구리 조회와 재시도/대기 안내, 환율 다시 확인, 오류 후 다시 시도, 차트의 각 시간 간격/다시 불러오기/확대·축소, 기록 표시, 모든 이동·출처 링크 |
| /verify.html | 금 조회·기록·검증, 저장 기록 새로 읽기, 실제 두 날짜와 변화값 대조, 증빙 JSON 다운로드와 내용, 실패·복구 전체 검사, 공식 개별 fixture 버튼과 전체 순서/초기화/재시도, 펼치기와 이동 링크 |
| /silver-verify.html | 은의 조회·기록·검증과 기록 읽기, 두 날짜/변화값, JSON, 실패·복구 검사, 화면에 존재하는 공식 검사 및 모든 조작 |
| /official.html | 올바른 검증 페이지로 이동하는지 |
| /task5.html | 비교표·증거 링크·현재 상태 링크, 과거 기록을 현재 성공으로 오해하게 표시하는지 |
| /handoff.html | 상태·시각·검사별 결과·다음 행동 표시, 최신 Actions와 정보판 링크 |

표의 여러 기능을 결과표 한 줄의 PASS로 뭉치지 않는다. 기능/선택값/시나리오별 ID와 결과를 남긴다. 현재 코드와 화면에 없는 기능은 근거와 함께 목록에서 구분한다.

- 정상 조회는 실제 외부 응답과 가격·단위·시각을 대조한다. 가짜 응답으로 실제 조회 성공을 대체하지 않는다.
- 실패·복구는 기존 합성 검사 또는 격리된 브라우저 세션의 네트워크 차단으로 확인하고 방법을 명시한다. 실제 정상 조회 결과와 합성 결과를 분리한다. 외부 서버 장애나 운영 데이터 손상을 일으키지 않는다.
- 오류 안내가 정상이어도 가격 조회 기능 자체가 실패했다면 가격 조회는 FAIL이다.
- 실제 두 날짜/대기 시간/정상 초기값 등 조건을 충족 못 하면 해당 시나리오는 미검사다. 날짜·가격·사용량·결과를 만들어 넣지 않는다.
- 저장 버튼의 쓰기 동작은 기존 앱의 정상 사용 범위에서 수행한다. 기존 증거 삭제·스키마 변경 등 파괴적 작업은 하지 않는다. 권한이 필요한 행동은 해당 항목만 보류한다.
- API 404 또는 기존 스크립트의 browser NOT_RUN을 이유로 다른 페이지 검사를 중단하지 않는다. 브라우저 자체를 사용할 수 없으면 가능한 코드/HTTP 검사는 하고 UI 항목은 UNVERIFIED로 남긴다.

## 3. 실패를 발견하면 수정과 재검사
오류 확인만으로 작업을 종료하지 않는다. 요청·응답, 화면, 콘솔 등 이용 가능한 증거로 원인을 조사하고 허용된 범위에서 수정한다. 수정 후 실패 항목과 영향을 받는 기능을 다시 실행한다. 마지막에는 전체 목록을 다시 검사한다.
고정 출처 변경 등 사용자 판단이 정말 필요하거나, 접근 권한·외부 서비스 복구·정해진 작업 상한 때문에 더 진행할 수 없으면 그 근거를 남긴다. 같은 실패 요청을 무한 반복하지 말고 시도·결과·배제한 원인·다음 구체적 행동을 기록한다. 막힌 한 항목 때문에 가능한 다른 검사를 생략하지 않는다.
로컬 수정이 배포되지 않았다면 로컬 결과와 기존 배포 결과를 구분하고 배포 후 검증은 미검사로 둔다.

## 4. 다음 AI에게 넘길 증거
[SITE-CHECK-TEMPLATE.md](SITE-CHECK-TEMPLATE.md)를 복사해 docs/handoff/site-check-latest.md를 작성한다. 매 시작/종료 검사 결과의 사본은 docs/handoff/site-check-history/<시각>-<고유구분>.md에 보존한다. 이전 결과를 지우지 않는다.
- 항목별 PASS / FAIL / UNVERIFIED(미검사), 실제 관찰, 기대값, 재현 행동, 증거 파일 경로를 남긴다. 실패는 가능하면 화면 캡처와 네트워크/콘솔 기록을 함께 남긴다. 없는 증거는 없다고 적는다.
- 개인정보·토큰을 제외한 증거만 docs/handoff/site-check-evidence/에 저장한다.
- npm run handoff:finish 실행 후 자동 생성된 current.md의 현재 상태·남은 문제·다음 행동에 이 보고서 링크와 미해결 항목 ID를 추가한다. 후속 finish가 요약을 덮어써도 별도 보고서와 이력을 읽어야 한다.
- 최종 답변에서 기능 수정 / 조사만 수행 / 문서 변경을 정확히 구분하고, 배포 검증 여부와 실패·미검사 수를 말한다. 조사 기록을 기능 수정본이라고 전달하지 않는다.
- 자동 gate가 전부 PASS여도 이 목록에 FAIL/UNVERIFIED가 있으면 “모든 기능 정상”이라고 말하지 않는다. 텍스트 규칙이며 CI가 이 보고서의 진실성이나 AI의 실행을 강제한다고 주장하지 않는다.
- 다음 AI는 이전 실패·미검사·시도 내역부터 읽고, 같은 시작 절차로 이어간다.
